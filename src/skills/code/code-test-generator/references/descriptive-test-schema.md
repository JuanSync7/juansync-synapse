# Descriptive Test Docstring Schema

Specification for the 5-tag docstring required on every test generated by the `code-test-generator` skill.
Loaded at the `[GENERATE]` node before test emission. Missing or malformed tags fail the validator
and the test is rejected by `code-test-evaluator`.

---

## 1. `@tests` — Fully-Qualified Target Under Test

**Purpose:** Identifies the exact callable being exercised. One target per test — no lists.

**Format:**

```
@tests: <module.path>:<symbol>
```

- Use Python dotted import path for the module (no leading dot).
- Separate the module path from the symbol with a colon (`:`).
- For methods, use `Class.method` as the symbol.
- One entry only. A test with multiple targets must be split.

**Examples:**

```
@tests: ragweave.text.normalizer:normalize_input
@tests: ragweave.pipeline.nodes.chunk:ChunkNode.run
```

---

## 2. `@scenario` — Input Condition / Branch / State Being Exercised

**Purpose:** One sentence describing the setup — what is true about the world when the test runs.
This is NOT a description of what the code does; it is a description of what is arranged.

**Format:**

- Imperative present tense, starting with "when".
- Single sentence, no period required.
- Describes inputs, preconditions, or system state — not expected outcomes.

**Good examples:**

```
@scenario: when input contains zero-width space and BOM markers
@scenario: when retry budget is exhausted and the upstream call keeps failing
@scenario: when payload size exceeds the configured max_bytes limit
```

**Anti-examples (bad):**

```
@scenario: when called                          # too vague — describes nothing
@scenario: tests that normalize works on text   # describes the test, not the setup
```

---

## 3. `@asserts` — Behavioral Assertions in Plain English

**Purpose:** Comma-separated list of what an outside reviewer would expect to hold after the test
runs. Written at the behavior level — not tied to line numbers or internal variable names.

**Format:**

- Comma-separated phrases, each describing one observable assertion.
- Use plain English: "returns X", "raises Y with Z in message", "calls handler exactly N times".
- Do not reference implementation details (line numbers, private variables, intermediate state).

**Good examples:**

```
@asserts: returns string with only printable chars, length decreases by exactly the count of stripped chars, no exception raised
@asserts: raises RetryExhaustedError, upstream call is attempted exactly 3 times, error message contains 'budget'
@asserts: raises ValueError with 'exceeds maximum' in message, no data is written to storage
```

**Anti-examples (bad):**

```
@asserts: asserts the function works correctly       # too vague — no observable claim
@asserts: line 47 returns x when self._buf is set   # implementation-coupled — not behavioral
```

---

## 4. `@layer` — Test Layer Classification

**Purpose:** Classifies the test into one of the recognized pyramid layers. Used by `code-test-evaluator`
for coverage gap analysis and by CI to route tests to the correct execution tier.

**Allowed values and definitions:**

| Value | Definition |
|---|---|
| `unit` | Exercises a single function or method in isolation; all external dependencies are mocked or stubbed. |
| `config` | Validates typed config contracts, default values, and contradictory-setting rejection. |
| `contract` | Verifies the public API surface (schemas, typed return shapes) against its declared contract. |
| `idempotency` | Asserts that repeated invocations with the same input produce identical output and side effects. |
| `mock-integration` | Exercises a multi-component flow with external I/O replaced by fakes or recorded fixtures. |
| `real-integration` | Runs against live infrastructure (Weaviate, Temporal, object storage); requires compose stack. |
| `property` | Uses property-based strategies (e.g., Hypothesis) to assert invariants over generated inputs. |

**Format:**

```
@layer: unit
```

---

## 5. `@generation_id` — Batch Trace Identifier

**Purpose:** UUID assigned to the code-test-generator batch that produced this test. Used to trace
generated tests back to their originating run and to audit coverage gaps.

**Format:**

- Full UUID or 8-character short prefix are both acceptable.
- Lowercase hex, no braces.

**Examples:**

```
@generation_id: a3f9c1b2
@generation_id: a3f9c1b2-4d7e-4f1a-9c3e-001122334455
```

## Full Template

```python
def test_normalize_strips_unicode_control_chars():
    """Normalize input strips unicode control characters.

    @tests: ragweave.text.normalizer:normalize_input
    @scenario: when input contains zero-width space and BOM markers
    @asserts: returns string with only printable chars, length decreases by exactly the count of stripped chars, no exception raised
    @layer: unit
    @generation_id: a3f9c1b2
    """
    ...
```

**Notes on the template:**

- The bare summary line ("Normalize input strips unicode control characters.") is permitted and
  recommended. It appears above the tag block and is treated as a human-readable description.
- One blank line separates the summary from the tag block.
- Tags appear in the order shown above; the validator accepts any order but the canonical order
  is `@tests`, `@scenario`, `@asserts`, `@layer`, `@generation_id`.

---

## Validation Contract

The `code-test-evaluator` skill parses all 5 tags via its docstring validator tool at review time.
The following rules are enforced:

- All 5 tags must be present.
- No tag may be empty or whitespace-only.
- `@tests` must match the pattern `<dotted.path>:<Symbol>` with exactly one colon and no commas.
- `@scenario` must begin with "when" (case-insensitive).
- `@asserts` must contain at least one comma-separated phrase longer than 3 words.
- `@layer` must be one of the 7 allowed values listed above; unknown values are rejected.
- `@generation_id` must be a hex string of 8 to 36 characters (short prefix or full UUID).

A test that fails any rule is **rejected** — it is not emitted to the output file and the
`[GENERATE]` node logs the failure with the tag and rule that caused it.

---

## Anti-Patterns

The following patterns fail validation and must not appear in generated tests:

| Anti-pattern | Tag | Reason |
|---|---|---|
| Tag absent entirely | any | Missing tag — hard failure |
| `@tests:` with no value | `@tests` | Empty tag |
| `@tests: mod:func_a, mod:func_b` | `@tests` | Multi-target — split into separate tests |
| `@scenario: when called` | `@scenario` | Too vague — describes no condition |
| `@scenario: tests that X works` | `@scenario` | Describes the test, not the setup |
| `@asserts: works correctly` | `@asserts` | No observable claim |
| `@asserts: line 47 returns x` | `@asserts` | Implementation-coupled |
| `@layer: integration` | `@layer` | Unknown layer — use `mock-integration` or `real-integration` |
| `@layer:` with no value | `@layer` | Empty tag |
| `@generation_id:` with no value | `@generation_id` | Missing batch trace — test cannot be audited |
